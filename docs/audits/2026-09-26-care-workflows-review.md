# Resident care and facility operations workflow review — 2026-09-26

This is review evidence for the comprehensive workflow pass; `BACKLOG.md` remains the planning register. The scope here covers resident care, clinical charting, eMAR integration, admission and move-in, dietary operations, incident/change follow-through, inspection/maintenance, emergency operations, resident finance, and resident guest/document workflows. Application route mounts, callers, query/mutation contracts, relevant SQL definitions, and existing regression suites were inspected. This document does not claim that every authenticated action was exercised against a running backend.

## Fixed defects

| Defect and reproduction | Change | Regression evidence |
| --- | --- | --- |
| Save an eMAR source without a credential, then try to finish setup. The console could only insert another source; it never supplied the existing `sourceId` to the save RPC. Existing sources also had no pause/restart controls. | Added per-source editing, credential replacement/unbinding, explicit status selection, and freshness validation. Opening the editor preserves setup, active, paused, disabled, and error states. Facility changes close stale editors; URL facility selections must belong to the scoped facility list. | `useMedicationIntegration.test.ts`: update identity/scope, stopping imports, invalid numeric thresholds, activation credential requirement, and status preservation. |
| Open `/app/residents/A/assessments/B` with a valid form ID belonging to resident B. The form was queried by ID alone but labeled and autofilled using resident A. | Require both resident ID and assessment form ID in the detail query and cache identity. An unrelated resident/form pair now fails before editing. | `useResidentAssessmentForms.test.ts`: mismatched resident fails; matching pair succeeds; missing route IDs disable the query. |
| Accumulate 1,000 newer work orders before an older unresolved repair. The older repair disappears from the maintenance queue and derived overdue/open counts. | Read all work-order pages with a unique ordering tie-break and identical filters on every page; fail the query if any page fails. | `useWorkOrders.test.ts`: older open repair after 1,000 closed records; second-page failure. |
| Emergency inventory can be added, but existing quantity, status, and expiration cannot be corrected or replenished. Re-adding creates duplicate stock records. | Added an update action using the existing inventory editor and scope-bound update (`id`, facility, organization); preserve existing notes, stamp the latest check, refresh readiness, and reject invalid quantities. | `useEmergencyOperations.test.ts`: update instead of insert, scope predicates, note preservation, invalid quantities, cache invalidation. |
| Inventory recorded as ready stays ready after its expiration date, and individual stock cards can show ready despite a quantity shortfall. | Derive readiness from recorded status, facility calendar date, and current/minimum quantities. Display expiration dates and use the same computed status for exception counts and cards. | `emergencyInventory.test.ts`: expired stock, expiration-day boundary, shortfall/replenishment, manually recorded warnings. |
| A resident with more than 1,000 financial transactions gets a partial balance and incorrect FIFO aging because older debt or credits fall off the API page. | Page the complete receivable ledger, statements, and personal-funds ledger with unique tie-breaks and resident filters. Any later-page failure fails the workspace rather than presenting a partial balance. | `useResidentFinancialOperations.test.ts`: 1,000 payments followed by an older charge retains the correct $200 outstanding balance and aging; older-page failure. |
| A daily service queue, active requirements register, or open-alert list exceeding 1,000 records silently loses the remaining work. Tabular RPCs are subject to the same API row cap as table reads. | Page all three collections with unchanged scope/date/status filters and stable unique ordering. The queue retains time-first scheduling priority and groups equal-time work by displayed resident name, service, then task ID. | `useResidentServiceTasks.test.ts`: 1,001 daily tasks, complete requirements and alerts, stable ordering/scope, and a later-page failure. |

Relevant existing browser suites include `resident-lifecycle`, `role-journeys`, `all-role-navigation`, `mobile-workflows`, `public-token-negatives`, and document-open workflows.

No live tenant records, medication feeds, financial transactions, signatures, or public guest grants were created or changed. Production eMAR synchronization, EHR writeback, signed storage downloads/PDF generation, email delivery, payment-provider handoff, cron-driven escalations, and actual guest-token expiry/revocation still require the configured backend and integrations. Source-level guards and mocked tests are evidence of implementation behavior, not proof that those external services are configured or reachable.

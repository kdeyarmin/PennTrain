### Auth cross-review: effective facility revocation

Cross-review of the refocus draft-preservation change found a cache-scope gap: an employee could retain a secondary facility's cached clinical chart after that assignment was revoked because the refreshed primary `employees.facility_id` stayed unchanged. The private session identity now also compares the resolved, sorted effective assignment set, while public `AuthUser.facilityId` keeps its existing meaning. Confirmed scope changes clear React Query and Supabase runtime caches; unchanged sets, initial unknowns, transient failures, and server idle/MFA restrictions preserve drafts and the last resolved comparison baseline.

`sessionFacilityScope` follows the actual SQL contracts: active employees get primary plus `employee_facility_assignments` access through `employee_serves_facility` / `clinical_record_visible`; facility managers and trainers use profile `facility_assignments` with active same-tenant facilities under `is_assigned_to_facility`. Those assignment tables have no effective-date columns. The separate effective-dated enterprise shadow memberships are not substituted for the compatibility access rules. All assignment pages are read until an empty page, advancing by the actual response count so a lower deployed API row cap cannot conceal a later assignment. Pre/post `current_session_unlocked` checks prevent temporary security-gate emptiness from being mistaken for revocation. The original primary-facility read is guarded too, and React Query retains its cached primary value on transient locked/MFA-denied reads.

Offline review showed that encrypted draft reads bind to organization/profile and do not recheck current facility assignments; a later server sync refusal cannot prevent local review/copy. A reload also has no previous in-memory assignment baseline, so clearing only when two observed scope sets differ misses assignments revoked while the app was closed. Full service-draft reads and both sync entry points now reconcile each draft against the current confirmed facility set. Scope-only changes remove excluded records while retaining allowed unsynced care records. The existing whole-store wipe remains for actual account/organization/role/deactivation and primary-facility identity changes.

Native vital-sign drafts are stored separately and have no facility ID. Their full reads and sync paths check the resident's current authorization with the existing `log_clinical_access` contract (`20260905260000_a_chart_read_that_left_no_trace.sql`), once per distinct resident in a batch. This logs the actual retained-observation review and removes records only for its exact scope-denial response after successful pre/post unlocked checks. Temporary MFA/idle restrictions, network errors, and otherwise unknown access preserve documentation. No historical facility is guessed, and discharged residents are not treated as unauthorized merely because the active chart picker omits them.

The auth context retains only the same identity's last resolved scope through a cache reset. Full-draft query keys include account, organization, and confirmed facilities, so an earlier unknown-scope result cannot populate the replacement query. Monotonic generation checks prevent stale decrypt/authorization work from deleting records after a scope or account replacement, including A-to-B-to-A transitions; auth callbacks invalidate old access immediately before React renders the new account. Scoped reads refresh the separate entry counts after reconciliation, and storage transaction failures remain errors.

All four IndexedDB entry/full queries also explicitly use React Query's `networkMode: "always"`. A real QueryClient reproduction showed each previously paused before invoking the local read when `onlineManager` was offline. Observation authorization makes no RPC while the browser reports offline, and inaccurate online status is bounded by one shared five-second budget for the whole resident batch. Each check receives only the remaining time and aborts at its deadline; subsequent residents remain unknown and retain their notes, while late responses cannot initiate further authorization requests.
